# CardTally Agent 可调用能力接口原则文档

## 1. 文档目的

本文档用于定义 CardTally 中 Agent 与产品能力之间的接口设计原则。

目标不是设计具体 API，而是明确以下问题：

- 哪些能力应支持 Agent 调用
- 哪些内容不应直接暴露给 Agent
- Agent 应调用“页面”还是“业务能力”
- 写操作应满足哪些约束

## 2. 核心结论

CardTally 中，Agent 不应直接调用页面层能力，而应调用稳定的业务能力接口。

更准确地说：

- UI 和 Agent 应共享同一套核心业务能力
- 页面只是能力的表现层
- Agent 不应依赖某个 Fragment、按钮或页面状态

一句话原则：

`所有核心业务能力，都应优先设计为可同时服务 UI 与 Agent 的能力接口。`

## 3. 为什么不能让 Agent 直接调用页面

如果 Agent 直接依赖页面层，会带来以下问题：

- 页面改版会连带破坏 Agent 能力
- UI 状态和业务状态耦合过深
- 难以审计 Agent 到底执行了什么
- 难以做权限控制与确认机制
- 难以复用到后续新入口

因此，页面层只能负责展示和交互编排，不应成为 Agent 的真实调用对象。

## 4. Agent 应调用什么

Agent 应调用的是“领域能力”或“应用服务能力”。

这些能力应具有以下特征：

- 语义明确
- 输入输出稳定
- 与 UI 表现解耦
- 能被审计
- 能被权限控制

## 5. 建议开放给 Agent 的能力类型

以下能力类型原则上应考虑支持 Agent 调用。

### 5.1 记录相关能力

- 创建记录
- 修改记录
- 查询记录
- 获取记录详情
- 删除记录
- 标记记录状态

### 5.2 资产相关能力

- 查询资产列表
- 获取资产详情
- 创建资产
- 修改资产
- 查询资产相关记录

### 5.3 分类与配置相关能力

- 获取分类列表
- 获取用户偏好
- 获取主题与展示偏好

### 5.4 Agent 辅助相关能力

- 生成建议
- 生成摘要
- 生成待确认事项
- 读取上下文信息

## 6. 不建议直接开放给 Agent 的内容

以下内容不应直接作为 Agent 的调用对象：

- Fragment
- Activity
- XML 布局逻辑
- RecyclerView 适配器行为
- 某个按钮点击事件
- 页面内临时 UI 状态
- 仅为视觉展示存在的临时结构

Agent 可以触发业务动作，但不应直接操纵页面实现细节。

## 7. 写操作原则

只读能力和写能力的风险不同，因此写操作必须更严格。

对 Agent 可触发的写操作，至少应满足以下要求：

- 明确输入参数
- 明确输出结果
- 可审计
- 可追踪触发来源
- 可确认或可修正

尤其是以下写操作要重点约束：

- 新增记录
- 修改记录
- 删除记录
- 创建资产
- 修改资产

## 8. 审计原则

所有由 Agent 触发的重要能力调用，都应能回答这些问题：

- 是谁触发的
- 什么时候触发的
- 调用了什么能力
- 输入了什么关键参数
- 产生了什么结果

如果这些问题答不清楚，就说明接口设计还不够稳。

## 9. 确认原则

对于高风险或会改写用户数据的操作，应默认需要确认机制，至少要支持以下之一：

- 执行前确认
- 执行后可修正
- 待确认状态

首版不必把确认机制设计得很复杂，但不能完全没有兜底。

## 10. 幂等与容错原则

Agent 调用的能力接口应尽量具备良好的幂等性和容错性，避免以下问题：

- 重复创建同一条记录
- 因一次异常导致数据半更新
- 因会话重试导致重复写入

这意味着接口在设计时应考虑：

- 是否支持重复提交保护
- 是否支持状态校验
- 是否支持安全失败

## 11. UI 与 Agent 的职责分工

推荐分工如下：

- UI 负责：展示、交互、引导、反馈
- Agent 负责：理解、建议、协作、触发能力调用
- 业务能力层负责：真正的数据读写与规则执行

这个分层必须稳定，否则后续无论 UI 改版还是 Agent 增强，都会互相拖累。

## 12. 首版落地建议

首版不需要一开始就把所有能力都开放给 Agent，但应优先把核心能力抽象好。

优先级建议：

1. 记录查询能力
2. 记录创建能力
3. 记录修改能力
4. 资产查询能力
5. 用户偏好读取能力
6. Agent 摘要与建议能力

也就是说，首版重点不是“开放一切”，而是“先把最关键的一层能力做成稳定接口”。

## 13. 架构结论

CardTally 的长期可维护性，取决于是否把“页面能力”与“业务能力”分开。

因此，应明确采用以下原则：

- 页面不是 Agent 接口
- 业务能力才是 Agent 接口
- UI 与 Agent 共享能力层
- 写操作必须可审计、可追踪、可修正

## 14. 结论

CardTally 不需要把所有 UI 行为都设计成 Agent 接口，但必须让所有核心业务能力具备被 Agent 调用的可能性。

这套原则的目标是：

- 保持基础产品清晰
- 支持 Agent 独立演进
- 避免 UI 与 Agent 强耦合
- 为后续能力扩展预留稳定基础
